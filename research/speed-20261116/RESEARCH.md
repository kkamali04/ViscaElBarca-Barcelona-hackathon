# Exact-preserving training-speed research

Snapshot: 2026-11-16. Public documentation only; Exa discovery and Firecrawl live retrieval (`maxAge=0`). No project implementation, dependency installation, restricted input, trained model, GT, fitting, or existing reports were read. The supplied baseline is `HistGradientBoostingClassifier(max_bins=63, max_iter=64)` with four threads. Installed package versions and the actual time breakdown remain unverified.

## Recommendation

Prioritize computing each identical, deterministic, label-independent preprocessing/feature stage once **within the same authorized attempt**, then reuse that result. Keep the estimator, training examples, split, labels, weights, feature order, numeric dtype, arithmetic and four-thread setting unchanged. This is a software reuse proposal, not a measured speedup or a new model.

An in-process run-scoped result is the simplest first option if memory permits. Disk caching becomes useful when results must outlive a stage/process or peak memory is a constraint. Cache only stages whose complete inputs and dependencies are explicit. A filename alone is insufficient identity: require input-content identity, ordered frames, full temporal context, schema, feature/configuration version and relevant environment/dtype information. Pure preprocessing can be shared only when its inputs really match; fitted preprocessing must remain split-specific. These are engineering inferences requiring implementation audit and blind acceptance, not guarantees from the documentation.

Measure total wall time and peak memory for the complete authorized attempt. If `T` contains repeated feature construction `k*F`, replacing it with one construction and reuse yields a potential saving of approximately `(k-1)*F - reuse_overhead`. If fitting itself occupies almost all of the reported twenty minutes, feature caching cannot remove most of that cost. No timings or savings were measured here.

| [HistGradientBoostingClassifier API](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingClassifier.html), scikit-learn 1.9.1 | Features are already converted into integer bins before training; `max_bins` is at most 255, plus a missing-value bin. `random_state` controls binning subsampling and the early-stopping split. `warm_start` reuses a previous fit and requires the same data for valid results. | Histogram compression already exists in the supplied baseline at 63 bins. Lowering bins or iterations changes the model. Public `fit` accepts sample features; this API does not document an external pre-binned-input contract. Avoid relying on private binning internals for an exact reuse patch. |
| [Parallelism and resource management](https://scikit-learn.org/stable/computing/parallelism.html), scikit-learn 1.9.1 | HGB uses OpenMP. Environment variables or `threadpoolctl` control native threads; `n_jobs` controls joblib work. Nested workers can oversubscribe CPUs, and more workers can hurt runtime. | Keep the existing four-thread setting for the initial reuse comparison. Treat changing thread count or process layout as a separate measured candidate. These docs establish controls, not a promise of bitwise identity or a guaranteed speedup. |
| [Copies and views](https://numpy.org/doc/stable/user/basics.copies.html), NumPy 2.5 | Basic slicing produces views; advanced integer/boolean indexing produces copies. Reshape may copy; flatten always copies. Views share their underlying data. | Reusing an already-created selection can remove repeated allocation without changing selected values/order. Do not replace an arbitrary selection with a slice unless equivalent. Shared arrays must not be mutated by another consumer; retain a copy where isolation is required. |
| [Disk-based caching / Memory](https://joblib.readthedocs.io/en/stable/user_guide/memory.html), joblib 1.6.0 | `Memory` persists function results for identical arguments, supports large NumPy arrays and hashes arguments. Read-only memory mapping can accelerate reloads. Compressed arrays cannot be memory mapped. Environment upgrades can invalidate cache entries. | Prefer an attempt-local cache for a pure stage; avoid hidden mutable state, ignored semantic arguments and path-only identities. Use read-only cached arrays; writable mappings can corrupt results. On Windows, release mapping references before cleanup. Hashing, first-write cost and reload cost require measurement. Use only locally created trusted cache files. |
| [numpy.savez_compressed](https://numpy.org/doc/stable/reference/generated/numpy.savez_compressed.html), NumPy 2.5 | `.npz` is a ZIP-DEFLATED archive containing `.npy` arrays; the example demonstrates exact array equality after loading. Numeric arrays can avoid pickle. | Lossless storage compression can preserve values, dtype and shape, but it is distinct from less model computation. It may trade disk I/O for CPU work; benchmark rather than assume a training improvement. Use numeric arrays and `allow_pickle=False` on supported pinned APIs; verify compatibility with the installed NumPy version. |

## Candidate order and acceptance boundary

1. Audit the actual stage boundaries and count identical feature/preprocessing calls; add aggregate stage timings without printing restricted values.
2. Reuse immutable results inside one attempt. Preserve original feature creation order and exact numeric operations; do not combine reductions, downcast, reorder rows or alter temporal context merely to save time.
3. Only if memory requires it, compare an uncompressed read-only local cache against in-memory reuse. Evaluate compression separately because decompression and hashing may erase its I/O benefit.
4. Freeze the candidate and use a fresh blind tester with independent synthetic fixtures. Require exact feature dtype/shape/order and byte equality where defined, deterministic repeated predictions/CSV, official validation, measured whole-attempt runtime/peak memory, and cache-mismatch/corruption safe failure or recomputation. Root must reproduce the actual results before calling the candidate verified.

Frame thinning, feature removal, float quantization/downcasting, fewer bins/trees, changed early stopping, split changes and warm-started refits are separate model/semantic experiments. They are not lossless reuse and need their own predeclared split and fresh held-out/blind validation. This research makes no hidden-performance claim and does not authorize another fit, publication or submission.
